# Utilities-opt: fx-CG50 性能研究基线

## 目标

在保持 Utilities 数据格式和主要用户功能兼容的前提下，针对 Casio fx-CG50：

1. 建立可重复的构建、功能回归和性能测试流程；
2. 找出启动、界面绘制、文件 I/O、日历搜索、压缩、JPEG 解码和 PicoC 的真实热点；
3. 降低峰值栈/RAM 使用、无效屏幕刷新和闪存写入次数；
4. 清理只适用于 fx-CG10/20 的硬件假设；
5. 每个优化都保留旧数据可读性，并在真实 CG50 上验证。

## 当前基线

- 上游基线：`v2.1`，commit `e1b64f607b28f6932f639d575d0d3fc667d87a54`。
- 本地分支：`codex/optimization`。
- 源码统计：约 31,114 行，38 个 C++ 文件，81 个 C 文件；包含 PicoC 测试和第三方组件。
- 最大应用文件：`calendarGUI.cpp` 2,303 行，`fileGUI.cpp` 1,234 行，`toolsGUI.cpp` 923 行，`calendarProvider.cpp` 868 行，`fileProvider.cpp` 805 行。
- 静态调用计数：`Bfile_*` 317 处，`MCS*` 52 处，`alloca` 89 处，`Bdisp_AllClr_VRAM` 35 处，`sprintf` 56 处，`strcpy` 104 处，`strcat` 111 处。
- 可重复审计入口：`tools/perf-audit.ps1`。它只读取源码，输出当前 revision、源码规模、高风险调用计数和所有 `alloca` 位置。

这些数字是源码扫描结果，不等同于运行时热点；运行时热点必须由 CG50 或兼容模拟环境中的计时数据确认。

## CG50 约束

官方资料显示，fx-CG50 的存储内存约为 16 MB，显示区域为 384×216 像素；当前官方支持页列出 fx-CG50 OS 3.81。性能目标因此同时包括：

- 输入到界面响应延迟；
- 首次启动和功能切换耗时；
- 峰值栈/RAM 和文件缓冲区大小；
- `.g3a` 代码/数据体积；
- 存储内存读写次数；
- 长时间运行和低电量下的稳定性。

## 已确认的兼容性风险

### 1. 硬件模型识别过时

`src/hardwareProvider.cpp` 的 `getHardwareModel()` 只识别 fx-CG10 和 fx-CG20，否则返回 `0`。CG50 的产品型号编码不同，因此系统信息页会显示 `Unknown`，其他未来依赖模型判断的逻辑也可能失效。

### 2. 直接内存地址访问

下列代码需要以 CG50 实机为准逐项验证，不能仅凭 CG10/20 行为推断：

- RTC 地址：`src/timeProvider.hpp`；
- CPU 频率寄存器：`src/hardwareProvider.cpp`、`src/powerGUI.cpp`；
- 用户信息、OS 信息和 Add-in 元数据：`src/memsysGUI.cpp`、`src/homeGUI.cpp`；
- 键盘/系统标志和锁屏寄存器：`src/keyboardProvider.cpp`、`src/lockGUI.cpp`。

`src/main.cpp` 已通过 `GetVRAMAddress()` 缓存 VRAM 指针，这部分符合 CG50 可移植性要求；不能重新改回固定的 `0xA8000000`。

另外，`src/keyboardProvider.cpp` 原先只接受 `0x88000000` 开头的系统例程地址。WikiPrizm 的 CG50 兼容实现同时接受 `0x88000000` 和 `0x8C000000`，本地分支已按此补上第二种安全范围；仍需在真实 CG50 上验证返回值和锁屏/菜单返回行为。

### 3. 构建环境与 SDK 版本差异

上游 `Makefile` 只面向旧版 `PrizmSDK/common/prizm_rules` 和 `common/prizm.ld`。本地分支现在兼容旧 SDK 与 `PrizmSDK-win-0.6` 的 `toolchain/prizm_rules` / `toolchain/prizm.x`，并加入了 `.github/workflows/build.yml`，由 GitHub Actions 在 Windows runner 上固定下载 SDK、构建并上传产物。

PicoC 的 Unix 测试 Makefile 还引用仓库中缺失的 `platform/platform_unix.c` 和 `platform/library_unix.c`，需要先修复测试入口或明确移除失效的主机测试路径。

## 性能测试矩阵

每项测试至少记录：冷启动时间、操作完成时间、首次响应时间、峰值栈/RAM、屏幕刷新次数、文件读取/写入次数、产物大小和异常情况。每个场景重复 5 次，报告中位数和最大值。

| 场景 | 测试数据 | 重点指标 |
|---|---|---|
| 冷启动 | 首次运行、已有设置、已有 20 个计时器 | 启动时间、设置/计时器加载、首帧时间 |
| Home 空闲 | 黑/白主题、状态栏开关 | 每分钟刷新次数、CPU/电池影响 |
| 日历月视图 | 0、20、100 个事件 | 文件读取、排序、绘制和峰值栈 |
| 日历搜索 | 当月、全年、跨年搜索 | 扫描时间、递归深度、临时缓冲区 |
| Tasks | 0、20、100 个任务 | 空列表路径、排序、写入次数 |
| 文件管理器 | 0、25、100、200 个条目 | 枚举、排序、菜单生成、峰值栈 |
| 文件内容搜索 | 1 KiB、24 KiB、64 KiB 文件 | 分块读取、边界匹配、用户中止响应 |
| 压缩 | 低/中/高重复率文件 | 五组参数试压缩的总耗时和读写量 |
| 文本编辑器 | 空文件、64 KiB 文件、长行 | 光标移动、查找、保存耗时和栈 |
| JPEG 查看器 | 小图、大图、不同色彩内容 | 解码耗时、临时缓冲区和刷新次数 |
| PicoC | 启动、文件扫描、循环、文件 API | 初始化耗时、解释器堆、退出稳定性 |
| TOTP/钱包 | 多钱包、多条交易、多个 TOTP | 哈希耗时、文件读写和数据完整性 |

## 优化顺序

### 阶段 0：可重复性

- 恢复或替换 PrizmSDK 构建入口；固定工具链版本和编译参数。
- 生成 `.g3a` 后保存代码/数据大小、符号和 map 信息。
- 修复 PicoC 主机测试，先让纯解释器测试能在 PC 运行。
- 增加不依赖硬件的日期、字符串、日历序列化、压缩和 TOTP 测试。

### 阶段 1：CG50 安全边界

- 增加 CG50 模型识别，但保留未知型号的安全降级路径。
- 对所有直接地址访问建立地址表和 OS/型号注释；优先改用 SDK syscall。
- 禁止在未确认目标容量前扩大栈上数组；特别审计 `alloca` 和递归目录/日历搜索。
- 统一检查 `Bfile_*`、`MCS*` 的返回值和短读/短写。

### 阶段 2：低风险性能优化

- 减少不必要的 `Bdisp_AllClr_VRAM` 和 `Bdisp_PutDisp_DD`。
- 把重复的菜单/文本临时对象改为可复用缓冲区。
- 让文件列表排序和内容搜索避免重复转换路径与重复打开文件。
- 压缩时只在确实需要时执行多组参数试压缩，并记录数据类型的最佳默认参数。
- 将大块临时缓冲区从深层调用栈移到受控工作区，避免峰值叠加。

当前最突出的栈风险不是普通小型局部变量，而是数据结构和缓冲区叠加：`CalendarEvent` 含 24/134/1030 字节的文本字段，按当前布局约 1,248 字节；100 个事件的数组约占 122 KiB。`saveVRAMandCallSettings()` 还会一次性保存约 144 KiB 的显示区域，压缩路径使用约 24 KiB 的输入缓冲区，PicoC 路径另有 128 KiB 的解释器工作区。它们应优先改成有明确生命周期的共享工作区或分块处理，但不能直接改变日历文件格式。

### 阶段 3：结构优化

- 将 `calendarGUI.cpp`、`fileGUI.cpp` 拆成视图、输入、存储协调几个单元。
- 把 GUI 对 `fxcg/*` 的依赖集中到平台适配层。
- 用显式的应用状态/屏幕返回值替代跨模块全局状态和隐式跳转。
- 将设置文件从“版本不匹配就全部重置”升级为逐字段迁移。

### 阶段 4：实机验证

- 在用户的 CG50 上记录 OS 版本、型号编码、系统信息和每项测试数据。
- 每次发布同时保留旧版 `.g3a`，先用副本数据目录验证，再替换正式版本。
- 对日历、钱包、TOTP、锁屏和文件操作做断电/异常退出恢复测试。

## 当前结论

现在最值得先做的是“工具链恢复 + CG50 兼容性探针 + 最小性能计时框架”，而不是立即重写大型 GUI 文件。没有这三项，任何速度提升都无法证明，也无法排除因 CG50 地址差异导致的假性性能问题或崩溃。
